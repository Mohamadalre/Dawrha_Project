# Dawrha Backend — خريطة الراوتات (Route Map)

مجموعة Postman بمجلدين رئيسيين فقط، وكلٌّ بداخله **مجلدات الأدوار** وكل دور راوتاته:

```
Dawrha Backend
├── Auth/                     ← مسارات المصادقة
│   ├── Admin
│   ├── Citizen
│   ├── Institutions
│   ├── Factory
│   ├── External Partner
│   ├── Collector / Driver
│   └── Shared (OTP / Password / Token / Session)
└── Home/                     ← مسارات التطبيق
    ├── Shared (أي مستخدم مسجّل)
    ├── Public (بلا توكن)
    ├── Admin
    ├── Citizen
    ├── Institutions
    ├── Factory
    ├── External Partner / Free Facility
    ├── Collector / Driver
    └── Odoo Webhooks (خادم↔خادم)
```

## الملفات
- `Dawrha.postman_collection.json` — المجموعة (Postman → Import).
- `Dawrha.local.postman_environment.json` — بيئة محلية (baseUrl + متغيّرات التوكنات).

## الاستخدام
1. Import للملفين، واختر البيئة **Dawrha — Local**.
2. اضبط `baseUrl` (افتراضي `http://localhost:3000`).
3. من **Auth** سجّل الدخول بالدور المطلوب، وانسخ `accessToken` إلى متغيّر الدور:
   `adminToken` / `citizenToken` / `institutionToken` / `factoryToken` / `externalToken` / `collectorToken`
   (و`tempToken` لـ OTP، `refreshToken` للتحديث، `odooWebhookSecret` لمسارات أودو).
4. نفّذ أي راوت من **Home** — العنوان والتوكن جاهزان.

## قواعد المسارات
- **البادئة**: كل المسارات تحت `/api`.
- **النسخة**: أغلبها `v1` → `/api/v1/...`. الاستثناء: **notifications** و**media** بلا نسخة → `/api/notifications/...` و`/api/media/...`.
- **الحماية**: `Bearer <token>` للمحمي؛ العامة (تسجيل/دخول/استعادة/محتوى/كتالوج عام) بلا توكن؛ مسارات أودو بسرّ الهيدر `x-odoo-webhook-secret`.

## توزيع الأدوار (من `ROLE_PERMISSIONS_MAP` الفعلي)
- **Citizen/Institutions/Factory/External** يتشاركون صلاحيات المشتري (الكتالوج/السلة/الاقتراح).
- **Institutions** تنفرد بـ `waste/category-requests` و`my-categories/my-materials`.
- **Factory & External** ينفردان بـ `products/:id/availability`.
- **Admin** يملك كل `admin.*`.
- **Collector** سائق: my-truck + استلام/تسليم + طلب تغيير وردية + مشاكل الشاحنة (لا صلاحيات مشتري).

## المرتبط بأودو (كله شغّال — موسوم `→/← Odoo`)
- **وارد** (webhooks بسرّ الهيدر): `fleet`, `driver-decision`, `shift-change-decision`, `inventory`, `warehouse` → 202 + job يعيد القراءة عبر JSON-RPC.
- **صادر** (طابور BullMQ يُطلقه راوت الدور): كتالوج/تسعير (Admin) · إنشاء مستودع (Admin) · طلب تغيير الوردية + إلغاؤه (Collector) · مشاكل الشاحنة (Collector) · **استلام/تسليم السيارة** (Collector) · دفع طلب السائق (اكتمال onboarding).

> عناوين `:param` تُستبدل بقيَم فعلية، وأجسام POST/PATCH نماذج تمثيلية تُعدَّل حسب الحالة.

## كوليكشن الأدمن — **مُولَّد لا مكتوب بيد**

`Dawrha.admin.postman_collection.json` يُبنى من سكربت:

```bash
node postman/build-admin-collection.js
```

**لماذا سكربت؟** لأن الكوليكشن المكتوب باليد **يتخلّف**. حين صارت حالات المادة تابعة
للمنتج، بقي الكوليكشن يعرض راوتات `/admin/waste/conditions` التي حُذفت — فمن يفتحه
يجرّب راوتات غير موجودة ويظن العطل في الباك ايند. والراوتات الجديدة (جدول التسعير،
المخزون، الاقتراحات) لم تكن فيه أصلاً.

بعد كل تعديل على راوتات الأدمن: عدّل السكربت وأعِد تشغيله.

**التحقق:** يشمله سكربت `verify-user-collection.js` نفسه (يفحص المجموعتين):

```bash
node postman/verify-user-collection.js
```

لكوليكشن الأدمن يُفحص **اتجاه واحد**: راوت موثَّق بلا كود خلفه — وهو العطل الذي
يهمّ، إذ يجرّبه القارئ فيحصل على 404 ويستنتج أن الباك ايند معطوب. أول تشغيل له
التقط راوت رحلات سائق التوصيل وقد كُتب فيه معرّف السائق **ثابتاً `1`**، فكان
يعمل فقط لو صادف وجود السائق رقم ١.

**النتيجة:** ١٠٢ طلب في ١٨ مجلداً، **١٠٢/١٠٢** موجودة في الكود.

## كوليكشن المستخدم — **مُولَّد ومُتحقَّق منه**

`Dawrha.user.postman_collection.json` — تطبيق **المواطن** وحده.

```bash
node postman/build-user-collection.js     # يبني
node postman/verify-user-collection.js    # يتحقّق مقابل الكود
```

**لماذا مجموعة مستقلّة؟** المجموعة الرئيسية تحمل الأدوار كلها معاً، وهي شكل صحيح
للاطّلاع وخاطئ للعمل: من يفتحها ليشتغل على تطبيق المستخدم يمرّ على ٥٨ راوت أدمن
و١٥ راوت سائق لا تخصّه، وما يخصّه مبعثر في ثلاثة مجلدات.

**الترتيب** كما يعيشها المستخدم لا كما رُتّبت الملفات:

```
0️⃣ زائر (بلا توكن)          6
1️⃣ تسجيل ودخول              4
2️⃣ تفعيل واستعادة           6
3️⃣ الجلسة والأجهزة          5
4️⃣ الملف الشخصي             3
5️⃣ العناوين                 4
6️⃣ الرئيسية                 5
7️⃣ البحث والسعر             2
8️⃣ العروض                   2
9️⃣ السلة                    6
🔟 الطلبات                   5
1️⃣1️⃣ تقييم وشكوى            2
1️⃣2️⃣ الإشعارات              7
1️⃣3️⃣ اقتراح مادة            1
1️⃣4️⃣ الصور                  5
1️⃣5️⃣ محتوى ثابت             2
```

كل طلب يحمل **وصفاً** يقول: ما يأخذه، وما يرجعه، ومن **أيّ جداول** يقرأ وأين يكتب —
والجزء الأخير هو ما لا يقوله التنقّل في Postman مهما طال.

### سكربت التحقّق

يقارن المجموعة بالكنترولرات في الاتجاهين:

- **MISSING** — راوت موثَّق بلا كود خلفه. **يُفشل** السكربت (exit 1).
- **EXTRA** — راوت يصله المواطن وغير موثَّق. تحذير، ومعه قائمة الاستثناءات المقصودة
  وسببُ كل واحد (أدمن، سائق، مؤسسات…).

وفيه تفصيلان لولاهما لكذب:
1. **الملف الواحد قد يحمل أكثر من كنترولر** — ملف الزائر يحمل اثنين (تطبيق المستخدم
   وتطبيق المصنع)، وملف طلبات التصنيفات يحمل كنترولر المشتري وكنترولر الأدمن.
   أخذ الأول وحده كان ينسب راوتات الملف كلها إلى مسار خاطئ.
2. **الراوتات قد تسكن صنفاً مجرّداً** — الزائر يعلن راوتاته الستّة في `abstract class`
   يرثه كنترولران رفيعان. تلك الديكوريترات تسبق أول `@Controller` في الملف.

**التحقّق:** ٦٥ طلباً في ١٦ مجلداً، **٦٥/٦٥** موجودة في الكود، ولا راوت مواطن بلا توثيق.
وجُرّب السكربت بالطفرة: إعادة تسمية `cart/items` إلى `cart/lines` في المجموعة
أظهرت المفقود والزائد معاً وأرجعت exit 1.
