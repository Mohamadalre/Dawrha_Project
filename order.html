تأكيد الاستلام والنقاط — السائق + المعمل

السائق يؤكد استلام كل مستودع، والمعمل يؤكد الاستلام الكامل فتُضاف النقاط — محقق بالكامل

محقق ✓ السائق يؤكد من المستودع

السائق (في Odoo) يؤكد استلام كل مستودع على حدة — يصل للباك اند كـ POST /odoo/webhooks/delivery event=picked_up → القطعة DISPATCHED. يتبعها ادمن المستودعات في واجهة Odoo، لا يراها ادمن الباك اند.

POST /api/v1/odoo/webhooks/delivery { event:"picked_up", backend_trip_id, backend_stop_id } → 202 → تكراره لكل مستودع حتى اكتمال الرحلة
محقق ✓ المعمل يؤكد الاستلام الكامل → نقاط

بعد وصول كل القطع DELIVERED، المعمل (FACTORY/EXTERNAL_PARTNER) يؤكد: POST /orders/:orderId/confirm-receipt → COMPLETED + points_awarded.

POST /api/v1/orders/3fa85.../confirm-receipt → { status:"COMPLETED", grand_total:3000, currency:"SYP", points_awarded:30, points_balance:128 }

الحساب: points = floor(grandTotal / amountPerPoint) — مثلاً amount_per_point=100 و grandTotal=3000 → 30 نقطة. يتم عبر PointsWalletService.awardForOrder (best-effort: الاستلام ينجح حتى بلا رصيد).

محقق ✓ الادمن يحدد قيمة النقطة

الادمن يحدد كم تساوي النقطة بالعملة لكل دور:

GET /api/v1/admin/points-rate → [{ role:"FACTORY", amount_per_point:"100.000", currency:"SYP" }] POST /api/v1/admin/points-rate { role:"FACTORY", amount_per_point:100 } // 1 نقطة = 100 عملة PATCH /api/v1/admin/points-rate/FACTORY { amount_per_point:100 } PATCH /api/v1/admin/platform-settings { default_currency:"SYP" } // العملة المركزية

العملة من platform-settings.default_currency، لا تُحدد لكل rate.

الفجوات الملاحظة — السيناريو مقابل الكود

مقارنة التفريغين الصوتيين بالكود المطبق في src/order — 3 فجوات، واحدة حرجة

فجوة 1 — تم إصلاحها ✓ بوابة مدير المستودعات للطلبات المقسمة
قبل الإصلاحبعد الإصلاح
allocate() ينشئ الـ parts فوراً بحالة OFFERED ويدفعها لكل مدير — تدخل الإدارة متزامن اختياري فقطللطلب المقسوم (plan.parts.length > 1) تُحفظ requestedLines ويوضع الطلب في AWAITING_SPLIT_APPROVAL دون إنشاء parts. مدير المستودعات يعتمد عبر POST .../approve-split (كما هو A+B) أو يعدل عبر .../modify (A+B→A+C) — حينها فقط تُنشأ الـ parts وتُدفع إلى Odoo

الملفات: enums/order-status.enum.ts (حالة جديدة) + providers/order-allocation.service.ts (تأجيل الإنشاء + approveSplit/createSplitParts) + admin-order.controller.ts (endpoint جديد)

فجوة 2 — متوسطة طلب التوصيل المقسوم: تجميع ثم توصيل مقابل milk-run
السيناريو (التفريغ الأول)الكود الحالي
الأبعد يرسل حصته إلى الأقرب، ثم سيارة واحدة من الأقرب للمشتري (تجميع وسيط + توصيل)التجميع مرفوض صراحة لطلب التوصيل (consolidationEligibility: 'is a delivery order'). بدلاً منه milk-run: شاحنة تبدأ من الأبعد وتمر بالأقرب وتصل محملة مباشرة

الأثر: نفس الهدف (شاحنة واحدة محملة) لكن آلية مختلفة — لا مرحلة تجميع وسيطة. قد يكون مقصوداً (أكفأ)، لكنه يخالف السرد.

الإصلاح المقترح: إما توثيق الـ milk-run كسلوك معتمد، أو السماح بتجميع لطلب التوصيل كمرحلة وسيطة ثم توصيل واحد من الأقرب.

فجوة 3 — طفيفة هوية مدير المستودعات

السيناريو يضعه في Odoo (مدير منطقة). الكود يحمي modify / modification-options بصلاحية backend محلية admin.orders.manage لحساب JWT — لا ربط بمفهوم مدير المنطقة في Odoo.

الإصلاح: ربط الصلاحية بدور Odoo أو توثيق أن مدير المستودعات = حامل صلاحية admin.orders.manage في الـ backend.

لا فجوة ما هو مطابق ✓
  • مستودع واحد يغطي → إسناد لأقربه مباشرة ✓
  • تقسيم بأقل عدد مستودعات وبأقل مسافة إجمالية، تعبئة الأقرب أولاً ✓
  • بدائل التعديل بنفس حجم التقسيم فقط (A+B ↔ A+C) ✓
  • تجميع الاستلام عند أقرب مستودع + تكلفة مسار التجميع ✓
